topic: UX документации HACS для Time Messenger integration
updated: 2026-08-11T21:23

- (decision) Основная аудитория уже умеет пользоваться Home Assistant и не нуждается в базовом обучении платформе.
- (decision) Типичный читатель технически уверен, немного гик и часто связан с разработкой или корпоративной IT-средой.
- (decision) Документация должна быть дружелюбной, приятной и лёгкой, а не ощущаться сложным талмудом.
- (decision) Желаемая эмоциональная метафора — хорошая детская книга: простая подача и лёгкость без инфантилизации технического читателя.
- (event) Discovery начат; аудитория и желаемое ощущение документации зафиксированы.
- (override) Не использовать вымышленного героя, persona storytelling или сюжет путешествия героя в документации и UX-контракте.
- (override) Метафора детской книги означает только лёгкость и ненапряжённость текста, а не сказочный сюжет или детскую стилизацию.
- (decision) Голос документации начинается с человеческого приветствия и говорит просто, без тяжёлого технического тона.
- (decision) Избегать длинных перечислений шагов в стиле «установить то-то, затем пятое-десятое» и стены инструкций.
- (decision) Читатель приходит уже мотивированным и примерно понимает назначение integration; README не должен долго продавать идею.
- (decision) Первые секунды README показывают конкретную пользу: сообщение коллеги запускает произвольную Home Assistant automation.
- (decision) Ключевые use cases: мигнуть лампой, озвучить уведомление через Яндекс Алису или колонку, отправить дополнительное уведомление.
- (decision) Главный пользовательский результат — не пропустить важное сообщение или письмо от коллег.
- (constraint) Use cases описываются как пользовательские Home Assistant recipes, а не как встроенные действия integration.
- (decision) Coaching path выбран по ходу интерактивного обсуждения UX документации.
- (decision) Основные поверхности чтения — GitHub README и HACS render_readme; контракт должен работать в обеих.
- (constraint) Технические SPEC, auth, architecture и research используются только как источники фактов и ограничений, не как образец голоса.
- (constraint) Документация показывает HA automation use cases, но не обещает встроенную поддержку Алисы, ламп или уведомлений.
- (constraint) Первый экран не перегружается auth, privacy и protocol-ограничениями; обязательные факты остаются доступными дальше по структуре.
- (event) Подтверждённые технические источники извлечены и привязаны к обоим UX spines.
- (decision) Сразу после коротких use-case тизеров читатель должен увидеть установку.
- (decision) Верх страницы содержит только краткие use-case тизеры; полные YAML recipes располагаются позже.
- (constraint) Перед установкой показывается только компактный обязательный compatibility fact Home Assistant 2026.8.1+, без отдельной тяжёлой технической стены.
- (decision) HACS custom repository — основной путь установки; manual copy остаётся recovery path по source contract.
- (decision) Сразу после установки документация объясняет выбор авторизации; первая automation идёт после успешного входа.
- (decision) Три auth mode объясняются различиями tenant policy, а не технической архитектурой integration.
- (decision) OAuth помечается как рекомендуемый, если он настроен организацией: refreshable access без хранения пароля.
- (decision) PAT подаётся как самый простой самостоятельный способ, если OAuth недоступен и personal tokens разрешены администратором.
- (decision) Session login подаётся как запасной способ; сохраняется только session token, но SSO policy может запретить API login.
- (constraint) Auth modes не показываются равнозначными и integration никогда не переключается между ними автоматически.
- (event) Пользователь подтвердил hierarchy авторизации: OAuth recommended, PAT simple self-service, Session fallback.
- (decision) Главный automation example — обычное уведомление как универсальный сценарий без device-specific dependency; затем свет и TTS.
- (decision) Оставшаяся Discovery переходит на fast path: неблокирующие детали фиксируются как предположения вместо дополнительных вопросов.
- (assumption) [ASSUMPTION] README использует только GitHub/HACS-native Markdown без custom CSS или custom frontend.
- (assumption) [ASSUMPTION] Визуальная лёгкость достигается короткими секциями, воздухом и понятными callouts, а не декоративной перегрузкой.
- (assumption) [ASSUMPTION] Русский — основной язык страницы; English ограничен обязательным коротким summary.
- (assumption) [ASSUMPTION] Документация одинаково читаема в HACS, GitHub desktop и mobile: без широких таблиц и информации только через цвет.
- (assumption) [ASSUMPTION] Motion отсутствует; изображения получают alt text, headings семантичны, code examples копируемы.
- (event) Discovery content decisions достаточны для fast-path distillation.
- (direction) Пользователь делегировал UX-мастеру оставшиеся вкусовые решения и не хочет промежуточных вариантов или дополнительных согласований.
- (decision) Optional multi-lens Reviewer Gate пропускается; применяется proactive rubric coverage и обязательный structure/prose polish.
- (decision) Creative mockups пропускаются по fast path: README реализуется native Markdown, а layout полностью задаётся spine-контрактами.
- (decision) Все README surfaces классифицированы spine-only; отдельная визуальная reference не нужна до непосредственной реализации README.
- (constraint) Финальные spines не используют вымышленного героя даже для Key Flows; task-based flows фиксируют явное пользовательское override.
- (decision) Делегированные пользователем fast-path assumptions приняты как финальные UX-решения; промежуточное согласование не требуется.
- (decision) Future README обязательно проходит humanizer draft, still-AI audit и final после factual/structural checks; публикуется только final.
- (constraint) Humanized README сохраняет все факты, code blocks и URLs; final не содержит em/en dash и перечисленных AI writing patterns.
- (event) Structure и prose review завершены; findings применены без изменения пользовательского intent.
- (event) Spines finalized.
