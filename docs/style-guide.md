# Стиль пользовательской документации

Правила для README и любой пользовательской (не разработческой) документации
этого проекта. Внутренние доки в `docs/` (архитектура, спеки) под эти
правила не подпадают: там приоритет у точности и ссылок на решения.

## Голос и тон

- Пиши как дружелюбный гайд, какие принято видеть на GitHub, а не как
  техническую документацию. Читатель может оказаться новичком в умном доме
  или опытным пользователем Home Assistant, и текст должен работать для
  обоих сразу, а не выбирать одну аудиторию в ущерб другой.
- Открывай текст конкретной пользой или узнаваемой ситуацией («пришло
  сообщение, и на кухне моргнула лампа»), а не архитектурой, авторизацией
  или списком ограничений. От пользы быстро веди к установке.
- Термин Home Assistant, который новичок мог не встречать (событие,
  автоматизация, сущность), можно напомнить одной фразой при первом
  употреблении. Это не превращает документ в учебник по HA, а просто
  убирает барьер входа для тех, кто только начал.
- Пиши живо и тепло, можно с лёгкой иронией, но без хайпа и без шуток за
  счёт точности фактов.
- Короткие абзацы, одна мысль на абзац. Никаких «стен» инструкций.
- Ограничения называй прямо, без драматизации, и не обещай того, что
  интеграция не делает (gap-free delivery, поддержка любого tenant и т.п.).

| Делать | Не делать |
| --- | --- |
| «Пришло сообщение в Time Messenger. Через пару секунд на кухне моргнула лампа.» | «Настоящая документация описывает архитектуру событийного pipeline…» |
| «OAuth рекомендуется, если его настроила ваша организация.» | «Выберите любой удобный способ. Интеграция переключится сама.» |
| «Не удалось войти: этот способ может быть отключён политикой сервера.» | «Unknown authentication failure.» |
| Короткое действие, затем причина или ограничение | Длинные предупреждения до первого полезного шага |

## Форматирование

- Только нативный Markdown GitHub/HACS — без custom CSS, широких таблиц и
  смысла, который передаётся только цветом.
- Заголовки строго H1 → H2 → H3, без пропусков; один H1 на страницу.
- `code` — только для команд, event payload и готовых YAML-примеров; жирный
  текст — для ключевого выбора или предупреждения, не для целых абзацев.
- Один эмодзи на заголовок секции допустим как визуальный якорь, но не в
  каждом пункте списка внутри неё. Он помогает быстро сканировать документ,
  а не украшает текст. Если сомневаешься, убери его.
- Значки (badges) в шапке README: не больше двух-трёх, только по делу
  (HACS, лицензия), без наборов ради красоты.
- YAML/автоматизации явно называй пользовательскими рецептами, а не
  встроенными функциями интеграции.

## Правило «не похоже на ИИ»

После фактической проверки перед публикацией финального текста убери:
em-dash и en-dash, рекламный ИИ-язык, искусственное «правило трёх»,
механические bold-списки, Title Case в заголовках, filler-фразы и
generic-заключения в духе «в заключение». Живой тон и ИИ-штампы не одно и
то же: тепло и конкретика остаются, лозунги и вода уходят. Черновики и
промежуточные версии в репозиторий не попадают, в нём остаётся только
финальный текст.
